Detecting Terraform Drift in Multi-Cloud Environments

Combine scheduled plans and cloud-native policy signals to find meaningful drift across Azure and AWS — without drowning the platform team in whitespace diffs.

TERRAFORM-DRIFT-DETECTION

Drift is the difference between declared configuration, Terraform state and deployed reality. Detect it with a scheduled, read-only pipeline for every workspace — not with a quarterly spreadsheet and a sense of foreboding.

Why drift happens

Someone fixes an incident in the portal at 3 AM. A managed service rotates a property you never declared. A policy engine mutates a resource on write. None of these are malicious, and all of them will eventually surprise a terraform apply.

  • Out-of-band changes made under incident pressure.
  • Provider defaults shifting between versions.
  • Policy or governance engines mutating resources after creation.
  • Resources created by another team inside a shared scope.

The detection pipeline

Run a read-only plan on a schedule and act on the exit code. This is the whole mechanism — everything else is reporting.

BASHdrift-check.sh 
terraform init -input=false
terraform plan -detailed-exitcode -input=false -no-color

Exit code 0 means no change, 2 means a diff exists, and 1 means the check itself failed. Store the plan output, open or update an issue for code 2, and alert the platform team separately for code 1 — a broken check is a different problem from a drifted resource.

■ MINER'S TIP

Treat exit code 1 as a page and exit code 2 as a ticket. Conflating them trains everyone to ignore both.

Reading the results

Exit codeMeaningAction
0No changesRecord the run, close any open drift issue
1Check failedAlert the platform team — credentials, state lock or provider fault
2Diff detectedOpen or update an issue with the plan attached

Cross-cloud signals

A plan only sees what Terraform manages. Pair it with native configuration evidence so you also catch resources nobody declared in the first place.

  1. Azure Policy compliance state for declared guardrails.
  2. AWS Config rules for the equivalent controls.
  3. Activity and CloudTrail logs to attribute the change to a principal.

Drift you cannot attribute is drift you cannot prevent. Always capture who alongside what.

Keeping the noise down

Baseline known-acceptable differences explicitly, with an owner and an expiry date. Anything permanent belongs in code; anything temporary belongs in a documented exception that expires on its own.

■ DO NOT

Never auto-apply a drift plan. The whole point of detection is that a human decides whether reality or the code is wrong.
